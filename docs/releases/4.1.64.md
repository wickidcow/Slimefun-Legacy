# Slimefun Legacy 4.1.64

This maintenance release builds on published 4.1.63. It retains the established Slimefun item and research IDs, typed persistent keys, storage identities, inventories, recipes, machine production rates and migration defaults. Minecraft 1.21.11 is the supported runtime floor, not an age limit for saved items or worlds.

## Core storage correction

When a block's pending removal is cancelled, pending deletions now reach the existing persistence scheduler as well as pending writes. Previously a deleted setting could disappear from the live cache yet remain in the database and return after restart. The private deletion marker exists only in memory; no new persisted marker or storage format is introduced. Empty strings remain real values. Permanently removed containers do not replay changes.

This fixes future cancellation handling; it cannot reconstruct deletions already lost before installation. It is not a redesign of cross-thread block removal or Folia region ownership.

## Coordinated maintained addons

The canonical 45-addon selection reconciles the independently completed addon branches as source-manifest revision 103. It retains the prior IE2/Networks lookup and storage-preservation work and includes:

- Networks 1.0.47: complete sort-mode cycling and immediate display-cache invalidation for changed filters/sort choices. Repeated equivalent choices and paging retain the cache. Storage contents, transfer priorities and quantum-storage category order are unchanged.
- BetterChests 1.0.3: conservative storage-adapter refusal, retained old item readers and exact Cargo mutation behavior, with loaded-only Doctor inspection.
- BuildingStaff 1.0.35: optional Rebar/Pylon placement and breaking using exact item payment, normal provider/protection events, and verified rollback before refunds. Providers remain optional and are not bundled. Their supported server versions are independent of the Slimefun floor.
- FluffyMachines 26.2.13: first-item barrel registration retained while either output buffer contains items, refusal of ambiguous saved state, private hover-label cleanup, and guarded item-frame interactions.

Every plugin is distributed as a raw standalone JAR from its own release repository; the aggregate ZIP is a convenience bundle containing the maintained plugin JARs and source/checksum records. Install only the addons already intended for your server, and replace old copies rather than leaving duplicate JARs.

## Compatibility and validation scope

Paper 26.3 is the primary API/support target; the tested channel is recorded in runtime evidence rather than assuming beta builds are stable. Paper/Purpur 26.2 and 1.21.11 remain backwards-compatibility lines. Core builds use Java 25 while retaining Java 21 plugin bytecode for the 1.21.11 floor. Leaf/Folia support and each addon's region safety remain qualified.

The release branch updates its previous-stable regression baseline to the exact published 4.1.63 source. The final versioned source must pass normal core/API/platform checks, the canonical 45-addon rebuild, provider-complete restart tests, and the existing two-clean-build reproducible-release gate before publication. A successful addon compile is not a substitute for those gates.

Focused core and addon tests include actual old-version data producers followed by upgrade and independent restart processes. They preserve typed item data and stored counts in their recorded fixtures. Tests using generated fixtures, mock API boundaries or synthetic player interfaces are individually attributed; they do not certify every populated customer world, external plugin interleaving, crash scenario, cross-fork rollback or future API.

See `docs/coordinated-addon-r103.md` and the linked repository checkpoints for exact test/source attribution. The consolidated addon ledger contains results from multiple runs, not a single complete gameplay test.

## Upgrade procedure

Stop the server cleanly. Back up the complete world, Slimefun database and addon data directories, then test the matching core and intended addon JARs on a disposable copy. Keep registrations and migration settings unchanged unless deliberately changing them. Inspect startup diagnostics and `/sf doctor` before attempting optional repairs or conversions.

Do not treat unreadable data as an empty inventory to replace. Restore or investigate the original record instead. Plugin rollback does not guarantee Minecraft world-version downgrade compatibility, and identical item IDs alone do not prove that every fork can read every serialized component.
