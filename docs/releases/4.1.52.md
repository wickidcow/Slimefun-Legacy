# Slimefun Legacy 4.1.52 — Storage Safety, Addon Integration & 26.3 Compatibility

Slimefun Legacy 4.1.52 consolidates the work completed after 4.1.51 into a clean release instead of continuing to mutate the older release. The focus is storage correctness, backpack safety, modern Paper/Purpur compatibility, integrated legacy functionality, and a fully rebuilt maintained-addon bundle.

## Storage and inventory safety

This release contains the full post-4.1.51 persistence hardening work.

Highlights include:

- inventory snapshots are acknowledged only after the exact database write batch completes
- failed or partially submitted inventory batches invalidate the persisted baseline and force deterministic reconciliation on the next save
- backpack storage reservations remain held through persistence instead of being released before writes are safely queued
- backpack writes are staged before snapshot refresh so failed writes remain visible and retryable
- asynchronous storage failures remain visible through shutdown instead of being silently lost
- higher inventory slots are explicitly deleted when menu sizes shrink
- delayed block and universal inventory writes clone the live ItemStack before serialization

### Empty ItemStack serialization race

Paper and Purpur can reject an inventory stack with:

`Empty itemstack cannot be serialized`

4.1.52 now uses Paper's native `ItemStack.isEmpty()` semantics before persistence, snapshots delayed inventory items before serialization, and normalizes Paper's exact empty-stack transition to Slimefun's normal empty-slot representation.

Unrelated serialization failures are still reported normally.

Regression checks now require these protections to remain present.

## Backpack safety

The backpack work after 4.1.51 closes additional item-movement and persistence races.

This includes:

- legacy backpack ownership preserved as part of reservation identity
- storage reservations held through the persistence boundary
- blocked session item-movement bypasses while a backpack is actively protected
- stronger ordering between cache/snapshot updates and database writes

The goal is to keep a single authoritative backpack state even during concurrent menu interaction, cache transitions, maintenance activity, and shutdown.

## Runtime conservation fixes

Several machine and world-resource paths now fail closed when an output cannot be safely committed.

This prevents successful world-resource consumption from being detached from its matching item output and strengthens transactional behavior around machine processing.

## Magic 8 Ball integrated into Slimefun Legacy

The historical Magic 8 Ball addon is now available directly through Slimefun Legacy with its existing item IDs preserved.

The integrated implementation:

- has its own Magic 8 Ball guide category
- can be enabled or disabled through the Slimefun Legacy addon configuration
- avoids loading the integrated copy when the standalone Magic 8 Ball plugin is present
- preserves legacy compatibility instead of creating replacement IDs

The standalone Magic 8 Ball JAR is therefore excluded from the canonical Slimefun Legacy addon bundle.

## Official optional resource pack

The optional Slimefun Legacy resource-pack pointer now uses the maintained official release URL:

`https://github.com/wickidcow/SFL_RP_Official/releases/latest/download/SlimefunLegacyRP.zip`

Modern item-model mappings were also realigned with the official resource pack so current Minecraft clients resolve the intended textures consistently.

Resource-pack delivery remains optional and disabled by default.

## Paper 26.3 and compatibility CI

The 26.3 compatibility system was expanded substantially after 4.1.51.

The release now includes:

- a canonical Paper 26.2 / 26.3 full-stack runtime comparison
- maintained-addon compile coverage aligned with the release bundle
- current Paper 26.3 candidate-family detection instead of pinning one stale prerelease
- explicit external addon hard-dependency handling in runtime smoke tests
- WorldEditSlimefun classification in the 26.3 compatibility matrices
- tighter addon-audit scoping so advisory instrumentation does not incorrectly fail the release gate

Paper 26.2 remains the production baseline. Minecraft/Paper 26.3 remains a compatibility target until stable-server validation and an explicit promotion decision.

## Canonical addon bundle

The canonical bundle remains:

`SF_Addons_1.21.11-26.3.zip`

Bundle revision **25** rebuilds the maintained addon set against the final 4.1.52 source and current Paper 26.3 candidate API.

Notable bundle work since 4.1.51 includes:

- Networks Legacy 1.0.21 refresh
- DracFun Reborn replacing the incorrect historical DracFun bundle entry
- BuildingStaff 1.0.34 English refresh
- WorldEditSlimefun added with explicit compatibility filename
- InfinityExpansion2 2.0.8 included with Mob Simulation hardening and the DynaTech duplicate MobDataCard registration fix
- Magic 8 Ball removed from the standalone bundle because it is integrated into Slimefun Legacy

The bundle still preserves the Minecraft 1.21.11 minimum compatibility floor while validating 26.3 separately.

## Release verification

4.1.52 keeps the hardened release rules introduced in 4.1.51:

- the core JAR is built twice from clean state and must be byte-for-byte reproducible
- Slimefun-owned bytecode must remain Java 21 compatible
- Paper 1.21.11 and Purpur 1.21.11 perform two-boot runtime validation
- Paper 26.2, Purpur 26.2, Folia 26.2, addon runtime smoke, gameplay correctness, API compatibility, and the 26.2/26.3 full-stack checks remain release gates
- the previous-stable regression baseline advances to the immutable 4.1.51 release commit
- release assets are normalized to exactly:
  - `Slimefun-Legacy4.1.52.jar`
  - `SF_Addons_1.21.11-26.3.zip`

Individual addon JARs remain on their own addon release pages instead of being published as Slimefun Legacy release assets.

## Upgrading

Stop the server normally and make a full backup before replacing the Slimefun core JAR.

After upgrading, perform a normal restart rather than `/reload`, review the startup log, and use the Doctor commands to inspect storage, runtime, dependencies, compatibility, and integrations before reopening a production server.
