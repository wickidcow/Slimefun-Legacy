# Slimefun Legacy 4.1.51 — Migration Safety, 26.3 Hardening & Release Cleanup

Slimefun Legacy 4.1.51 rolls the post-4.1.50 maintenance work into a proper core release instead of continuing to refresh the old 4.1.50 tag. The focus is safer legacy-data migration, cleaner Paper-family compatibility, and a release layout that keeps Slimefun Legacy separate from its standalone addons.

## Doctor and legacy-data migration

The Doctor migration system now covers the structured Slimefun persistence paths that can retain legacy IDs or serialized ItemStacks after an upgrade.

Highlights include:

- fingerprinted persisted block-ID migration for unloaded `BLOCK_RECORD` entries
- matching persisted ID migration for `UNIVERSAL_RECORD` entries
- safe serialized ItemStack migration for block and universal inventories
- persisted backpack Item-ID migration with cache/maintenance locking so active backpacks are not rewritten behind live gameplay state
- an addon-facing loaded-machine migration provider lane for exact semantic machine migrations
- short-lived, single-use migration plans with stale-data revalidation before execution
- rollback handling for partially applied storage changes
- no forced chunk loading for storage-level migration scans
- unknown, ambiguous, unreadable, loaded, or otherwise unsafe records remain unchanged and are reported instead of guessed

The upgrade workflow and Doctor reporting now distinguish storage that is ready to migrate from storage that is cached/deferred or requires manual review.

## Storage migration coverage guard

CI now verifies that every structured core persistence field that stores a Slimefun identity or serialized ItemStack is deliberately covered by the migration system.

This protects future schema work across SQLite, MySQL, and PostgreSQL from silently introducing a new persisted identity or item-payload scope without a matching migration decision.

Opaque addon-owned key/value data is intentionally not treated as a generic Item-ID migration target.

## Paper 26.3 compatibility hardening

Two remaining implementation-detail dependencies were removed while preserving existing behavior:

- legacy Paper `PlayerProfile` casting was removed from old ItemMeta/skull recovery
- `ThreadUtils` no longer reflects into Paper's internal `MCUtil.MAIN_EXECUTOR`

Paper continues to use the Bukkit/Slimefun scheduler path, while Folia keeps its global-region scheduler behavior. These changes reduce reliance on Paper internals that may move or disappear in 26.3.

The compatibility floor remains Minecraft 1.21.11. Paper 26.2 remains the production baseline while 26.3 compatibility is validated through the candidate/pre-release CI paths.

## Backpack and persistence safety

Backpack maintenance now coordinates direct storage work with live cache misses and profile storage activity. Doctor migration fails closed when the authoritative state cannot be proven safe, rather than waiting on gameplay-thread database activity or writing around a live cached backpack.

Additional regression coverage protects cache installation, maintenance exclusion, rollback behavior, empty ItemStack serialization handling, and migration fingerprint stability.

## Canonical addon bundle

Slimefun Legacy releases now use one maintained compatibility bundle:

`SF_Addons_1.21.11-26.3.zip`

The bundle is built from the maintained `wickidcow/SF_*` addon matrix, compiled against the current Slimefun Legacy/Paper compatibility stack, and includes a manifest and checksums for the exact addon JAR set.

Individual addon JARs are **not** published as Slimefun Legacy release assets. Each addon remains responsible for its own standalone release page.

A Slimefun Legacy release is now intentionally limited to:

- `Slimefun-Legacy4.1.51.jar`
- `SF_Addons_1.21.11-26.3.zip`

The old `SFL_AddonsNDependencies.zip` publisher chain and targeted bundle refresh workflows have been retired so stale addon versions cannot be pushed back onto a current Slimefun Legacy release.

## Release verification

The core release workflow still requires two clean builds to be byte-for-byte identical before publication. It also verifies the Java 21 bytecode target and release packaging.

Before publishing the addon bundle beside the core JAR, the release workflow verifies the bundle's GitHub SHA-256 digest, ZIP integrity, `SF_ADDON_MANIFEST.json`, exact addon JAR set, canonical `SF_*.jar` naming, and the declared 1.21.11 through 26.3 compatibility range.

After publication, release assets are normalized and the workflow fails unless the release contains exactly the Slimefun Legacy core JAR and the canonical addon bundle.

## Upgrading

As with any storage migration release, make a server backup before running Doctor migration execution commands. Scans are designed to identify what can be migrated safely; records that cannot be proven safe are deliberately left untouched for review.
