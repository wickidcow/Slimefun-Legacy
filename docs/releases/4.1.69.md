# Slimefun Legacy 4.1.69

This maintenance release adds a guarded recovery path for backpacks that Slimefun Legacy intentionally refuses to load because Minecraft can no longer deserialize one or more stored items. It uses the published 4.1.68 source, `54937520cb8c0f7cd63f96365085e2a15981ce9f`, as its release-blocking compatibility baseline.

## Backpack quarantine recovery

A removed datapack, mod or plugin can leave historical ItemStacks containing registry-backed data that the current server no longer recognizes. Minecraft then refuses to deserialize the affected item before Slimefun can construct the backpack inventory. Legacy already protects these cases with an incomplete-load hold so a failed read cannot be saved back as an empty or partial backpack.

4.1.69 adds an explicit operator recovery lane for cases where restoring the missing dependency is impossible:

```text
/sf doctor storage backpacks scan <backpack-uuid>
/sf doctor storage backpacks quarantine <backpack-uuid> <full-fingerprint>
```

The scan is read-only. It inspects one stored backpack without publishing a partial inventory, reports only unreadable rows, and produces a SHA-256 fingerprint covering the complete stored backpack state plus the exact unreadable candidate set.

Quarantine is deliberately destructive and requires the exact fresh fingerprint. It is allowed only while the backpack remains under a failed-load hold, is not cached/live, and has no pending backpack save chain. The mutation owns the existing exclusive backpack-maintenance gate so a normal cache-miss load cannot race the recovery operation.

Before deleting anything, Legacy writes the exact raw payload of every targeted unreadable row to a ZIP under:

```text
data-storage/Slimefun/recovery/backpacks/
```

If the archive cannot be created, no row is deleted. Successful quarantine removes only the unreadable inventory rows. The backpack profile, UUID, owner, name, size and healthy stored rows are preserved.

The incomplete-load hold is intentionally retained after quarantine. A normal complete backpack load must succeed before Legacy releases that hold. If another unreadable row becomes visible after the first recovery pass, the owner must run a new scan and use its new fingerprint.

## Storage safety

This release does not add an automatic force-clear path. `/sf doctor repair confirm` remains presentation repair and does not bypass incomplete-inventory protection. Generic storage-integrity repair remains separate from backpack quarantine.

No item or research IDs, database table schemas, stored field names or types, backpack identities, inventory codecs, recipes, capacities, machine rates, Cargo priorities, energy behavior or migration defaults are changed by this feature. Existing healthy backpacks continue through the normal load/save path.

## Installation

Stop the server normally and keep a complete backup of worlds, player data, Slimefun data and databases before replacing the core. Use a full restart, never `/reload`.

For an unreadable backpack, first inspect:

```text
/sf doctor storage recovery
/sf doctor storage backpacks scan <backpack-uuid>
```

Restoring the missing dependency remains preferred whenever possible. Use quarantine only when that is impossible and losing the unreadable item row is an accepted recovery choice.
